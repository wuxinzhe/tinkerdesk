# 13-前端消息上传拦截器体系

> 涵盖：分片拦截、尺寸限制、可扩展拦截器链

## 1. 问题背景

前端有多个消息上行通道（user_message、tool_result、approval_response、revoke 等），都通过 `backend.send()` → `ws-client.ts` → STOMP publish 发送到服务端。

当前没有任何尺寸检查，导致：
- **大消息（>256KB）** 触发 WebSocket 1009 断连
- **超大消息（>1MB）** 不可恢复，用户无感知
- **所有通道一视同仁**，无法区分"大负载可分片" vs "控制类直接挡回"

需要在前端构建一个可扩展的拦截器管线，在 `backend.send()` 和 `client.publish()` 之间插入拦截逻辑。

## 2. 架构总览

```
backend.send(msg)
    ↓
ws-client.send(msg)
    ↓
 ┌──────────────────────────────────────┐
 │  InterceptionPipeline                │
 │                                      │
 │  按 type 分派给对应的 handler        │
 │                                      │
 │  handler(msg, next)                  │
 │    ├─ handler 可调 0~N 次 next()     │
 │    │   (0 = 拒绝, 1 = 直传, N = 分片)│
 │    └─ 无 handler → 直接 next()       │
 │                                      │
 └──────────────────────────────────────┘
    ↓
client.publish(destination, body)
```

## 3. InterceptionPipeline 管理类

### 接口定义

```typescript
type PublishFn = (msg: OutgoingMessage) => void

interface OutgoingMessage {
  type: string         // 'user_message' | 'tool_result' | 'approval_response' | 'revoke' | ...
  [key: string]: unknown
}

interface MessageHandler {
  /** 处理一条上行消息。通过调 next() 放行（可多次），不调则拒绝 */
  handle(msg: OutgoingMessage, next: PublishFn): void
}

class InterceptionPipeline {
  private handlers = new Map<string, MessageHandler>()
  private fallback: MessageHandler | null = null

  /** 注册 handler，按 type 路由 */
  use(type: string, handler: MessageHandler): this

  /** 设置兜底 handler（当 type 无匹配时） */
  setFallback(handler: MessageHandler): this

  /** 管线入口 */
  intercept(msg: OutgoingMessage, publish: PublishFn): void
}
```

### 生命周期

```
pipeline.intercept(msg, publish)
  → 查 handlers.get(msg.type)
    ├─ 有 → handler.handle(msg, publish)
    └─ 无 → fallback?.handle(msg, publish) ?? publish(msg)
```

### 扩展方式

新增一个上传通道，只需：

```typescript
// 1. 新建处理器文件
// src/renderer/utils/interceptors/my-handler.ts

// 2. 在初始化入口注册
pipeline.use('my_new_type', new MyHandler({ ... }))
```

不修改任何旧文件。

## 4. 内置 Handler

### 4.1 ChunkHandler — 分片处理器

适用范围：`user_message`、`tool_result` 等可能携带大负载的通道。

#### 策略

| 尺寸范围 | 行为 |
|---------|------|
| ≤ 200KB | 直传，调一次 `next(msg)` |
| 200KB ~ 1MB | 分片传输，调 N 次 `next(chunkMsg)` |
| > 1MB | 拒绝，弹 Error 弹窗提示用户自行切分 |

#### 分片协议（wire format）

```typescript
interface ChunkMessage {
  type: 'chunk'
  /** 原始消息类型，服务端重组后恢复路由 */
  originalType: string
  /** 全局唯一分片 ID，同一消息的所有分片共享 */
  chunkId: string
  /** 从 0 开始的片序号 */
  chunkIndex: number
  /** 总分片数（在最后一帧下发，供服务端校验完整性） */
  totalChunks: number
  /** 分片负载：原始 payload 的一部分 */
  payload: unknown
}
```

#### 分片流程

```
msg (type='tool_result', result='<800KB>', ...)
    ↓
ChunkHandler.handle(msg, next)
    ├─ JSON.stringify(msg) → body
    ├─ body.length ≤ 200KB → next(msg)  ← 直传
    ├─ body.length > 1MB → showErrorToast(...)  ← 拒绝
    └─ 200KB < body.length ≤ 1MB →
         chunkId = uuid()
         遍历 body 每 200KB 一段
         for each 段 → next({ type: 'chunk', originalType, chunkId, chunkIndex, totalChunks, payload })
         store.chunkBuffer[chunkId] = { type: 'chunk', ... }  // 记录上下文
```

### 4.2 SizeLimitHandler — 限尺寸处理器

适用范围：`approval_response`、`revoke` 等控制类轻量通道。

#### 策略

| 条件 | 行为 |
|------|------|
| ≤ 200KB | 直传 |
| > 200KB | 拒绝 + error 弹窗（防篡改注入） |

```typescript
class SizeLimitHandler implements MessageHandler {
  constructor(private options: { maxAllowed: number }) {}

  handle(msg: OutgoingMessage, next: PublishFn): void {
    const body = JSON.stringify(msg)
    if (body.length <= this.options.maxAllowed) {
      next(msg)
    } else {
      showErrorToast({
        code: 'MSG_TOO_LARGE',
        message: `消息体过大（${body.length} bytes），${this.options.maxAllowed} bytes 以内允许发送`
      })
    }
  }
}
```

## 5. 各通道注册表

| type | handler | maxDirect | maxAllowed | 理由 |
|------|---------|-----------|------------|------|
| user_message | ChunkHandler | 200KB | 1MB | 用户可能粘贴大文本 |
| tool_result | ChunkHandler | 200KB | 1MB | 工具执行结果可能很大（ls -la、大文件） |
| approval_response | SizeLimitHandler | — | 200KB | 仅 `{toolCallId, approved, sessionId}`，无理由超 1KB |
| revoke | SizeLimitHandler | — | 200KB | 仅 `{type, sessionId, messageId}` |
| (其他控制类) | SizeLimitHandler | — | 200KB | 默认防护 |

## 7. 服务端重组

分片消息抵达服务端后，由 STOMP listener / handler 统一处理：

```
收到 type='chunk' 的消息
  → chunkBuffer[chunkId].parts[chunkIndex] = payload
  → 若已收齐所有分片（以 totalChunks 为准）
    → 按 chunkIndex 排序拼接得到完整 body
    → JSON.parse → 恢复原始消息结构
    → 以 type = originalType 重新进入正常处理流程
```

### 服务端防护

| 风险 | 策略 |
|------|------|
| 收不全 | 30 秒超时 → 丢弃缓冲区 |
| 内存溢出 | 每连接最多 50 个未完成分片组 |
| 重复分片 | 按 chunkIndex 去重（后到覆盖先到） |

## 8. ws-client.ts 改动点

```typescript
// ws-client.ts

class WebSocketClient {
  private pipeline = new InterceptionPipeline()

  constructor() {
    this.pipeline.use('user_message', new ChunkHandler({ maxDirect: 200 * 1024, maxAllowed: 1024 * 1024 }))
    this.pipeline.use('tool_result', new ChunkHandler({ maxDirect: 200 * 1024, maxAllowed: 1024 * 1024 }))
    this.pipeline.use('approval_response', new SizeLimitHandler({ maxAllowed: 200 * 1024 }))
    this.pipeline.use('revoke', new SizeLimitHandler({ maxAllowed: 200 * 1024 }))
  }

  send(msg: unknown): void {
    // ... 原有序列化+enrich逻辑 ...
    const enriched = { ...parsed, clientMessageId }
    const enrichedJson = JSON.stringify(enriched)

    // 新：走拦截器管线
    this.pipeline.intercept(enriched, (finalMsg) => {
      const body = JSON.stringify(finalMsg)
      // ... 走原有 publish 逻辑 ...
      this.client.publish({ destination, headers, body })
    })
  }
}
```
